| **1** | **CQRS vs Event Sourcing: 데이터 일관성 확보 비용 트레이드오프** | "어떤 방식으로 데이터의 변경 이력을 관리하는 것이 가장 효율적인가? 개발 복잡도 대비 얻는 안정성은 무엇인가?" | **[주요 논점]** 1. **복잡도 vs 안정성:** CQRS는 비교적 구현이 직관적이나, Event Sourcing은 비즈니스 로직을 이벤트 중심으로 강제하여 장기적인 시스템 안정성이 높다는 논쟁이 주를 이룸. 2. **데이터 조회(Query):** Event Sourcing의 단점인 '읽기 모델(Read Model)' 구축 및 동기화 과정의 복잡도를 해결하는 방안 제시가 필수적임. |
| **2** | **Service Mesh 도입 시 운영 책임과 초기 비용 분석** | "서비스 간 통신 복잡도가 높아졌는데, Istio 같은 Service Mesh를 도입하는 것이 과연 가치가 있는가? 초기 학습 비용과 운영 부하를 분석해 달라." | **[주요 논점]** 1. **오버 엔지니어링 경고:** 작은 규모의 서비스에는 과도한 오버 엔지니어링일 수 있다는 경고가 많음. 2. **트래픽 관리:** A/B 테스트, 카나리 배포, 서킷 브레이커 등 고급 트래픽 제어 기능이 핵심 가치로 다뤄지며, 이를 위해 필요한 운영 역량(DevOps 숙련도)이 전제 조건으로 강조됨. |
| **3** | **GraphQL vs REST: 프론트엔드 개발 속도 및 데이터 요청 최적화 비교** | "클라이언트가 필요한 데이터만 정확히 가져오려면 어떤 방식이 좋을까? API 엔드포인트 폭증을 막는 가장 좋은 방법은 무엇인가?" | **[주요 논점]** 1. **Over-fetching 문제 해결:** GraphQL의 가장 큰 장점(필요 데이터만 요청)을 강조하며, REST의 오버-페칭 문제를 해결하는 데 초점을 맞춤. 2. **배포 및 캐싱:** REST는 캐싱 전략이 직관적이지만, GraphQL은 스키마 변경 시 클라이언트/서버 양쪽 모두에서 고려할 부분이 많아 개발 속도 측면에서 논쟁이 발생함. |
| **4** | **Kafka vs RabbitMQ: 실시간 데이터 파이프라인 구축 시 메시지 영속성 차이** | "스트리밍 데이터를 처리할 때, 메시지를 보장받고 순서대로 처리하는 것이 중요한가? 메시지 큐잉 시스템 중 무엇을 선택해야 하는가?" | **[주요 논점]** 1. **확장성 및 영속성:** Kafka는 분산 로그(Distributed Log) 기반으로 엄청난 쓰기 부하와 높은 영속성, 확장성을 자랑하며 대용량 데이터 파이프라인에 적합하다는 평가가 지배적임. 2. **메시징 패턴:** RabbitMQ는 전통적인 메시지 큐(Message Queue)의 패턴(라우팅, ACK 기반)을 따르므로, 단순한 작업 요청(Job Queue) 처리에는 더 적합하다는 구분이 핵심임. |
| **5** | **BFF(Backend For Frontend) 패턴 도입의 아키텍처 이점과 유지보수 복잡도** | "프론트엔드마다 개별 API를 만들 때 발생하는 문제를 해결할 수 있는가? BFF를 만들면 백엔드가 과부하되는가?" | **[주요 논점]** 1. **클라이언트 최적화:** 각 클라이언트(웹, 모바일 iOS, 모바일 Android)에 최적화된 API 레이어를 제공하여, 클라이언트의 데이터 요청과 백엔드의 복잡한 구조를 분리하는 것이 핵심 이점임. 2. **추가 레이어:** BFF 자체가 추가적인 배포 및 관리 레이어가 되므로, 아키텍처 복잡도를 증가시키고, 이 BFF를 누가 관리할 것인가(운영 책임)에 대한 고민이 늘 필요함. |
