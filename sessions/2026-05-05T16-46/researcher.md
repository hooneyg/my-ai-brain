### 📌 주제 1: Event Sourcing vs. CQRS
**[포지셔닝]** 데이터의 진실(Source of Truth)과 쿼리 구조의 분리라는, 데이터 엔지니어링의 핵심 논쟁 지점.
**[핵심 청중 의도]** "우리가 저장하는 것이 진짜 데이터인가? 데이터를 조회할 때 성능 이슈가 생기면 어떻게 해결해야 하는가?"

| No. | 비교 포인트 (Comparison Point) | Event Sourcing (ES) | CQRS (Command Query Responsibility Segregation) | 운영 책임 관점 (Op. Responsibility) | 비용 트레이드오프 (Cost Trade-off) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1** | **데이터 모델 (Storage)** | 모든 상태 변화를 이벤트 로그로 저장 (Append-Only). | Command와 Query를 위해 서로 다른 데이터 모델(Read/Write DB) 사용. | **ES:** 데이터 불변성이 높고 감사(Audit) 기능이 내재되어 있어 운영 관리가 용이함. | **CQRS:** 리드 모델 최적화를 위해 별도의 NoSQL/Graph DB 도입 비용 발생. |
| **2** | **일관성 모델 (Consistency)** | 이벤트를 통한 **최종 일관성(Eventual Consistency)**이 기본. | Command와 Query를 분리하여 어느 정도의 일관성을 제어 가능. | **ES:** 복잡한 비즈니스 로직에 대한 상태 변화 추적이 용이하여 운영 관리가 명확함. | **CQRS:** 일관성 레벨에 따라 복잡한 동기화 로직(Saga 패턴 등) 구현 비용이 발생. |
| **3** | **쿼리 복잡성 (Query Complexity)** | 쿼리마다 이벤트를 재처리(Replay)하거나 Materialized View를 구축해야 함. | Query 모델에 특화된 최적의 데이터베이스를 사용하므로 쿼리 설계가 직관적임. | **ES:** 쿼리 요구사항이 늘어날수록 리플레이 로직 및 View 관리가 복잡해짐. | **CQRS:** 쿼리 요구사항 증가 시, 단순히 리드 DB만 확장하면 되므로 상대적으로 운영 부담이 적음. |
| **4** | **비즈니스 로직의 경계** | 비즈니스 로직 자체가 이벤트 발생에 의해 정의되므로 경계가 명확함. | Command 핸들러가 비즈니스 로직의 경계를 정의하며, Query는 단순 조회에 집중함. | **ES:** 상태 변화를 기반으로 하므로, 누가 어떤 변화를 일으켰는지 책임 소재가 명확함. | **CQRS:** Command와 Query를 별도 팀/서비스로 분리하여 개발 속도와 책임 분리가 용이함. |
| **5** | **구현 복잡도 (Implementation)** | 이벤트 스토어, 이벤트 리스너, 이벤트 매퍼 등 고도화된 패턴 지식이 필요. | Command/Query를 분리하는 아키텍처 설계와 데이터 매핑 레이어 설계가 핵심. | **ES:** 초기 학습 곡선과 아키텍처 설계 난이도가 매우 높음. | **CQRS:** 기본적으로 분리된 구조이므로, 초기 아키텍처 설계 후 구현은 상대적으로 예측 가능함. |
