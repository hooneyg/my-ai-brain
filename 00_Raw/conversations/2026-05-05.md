## 💡 [후크/도입부] 당신의 시스템은 '진짜' 상태를 기억하고 있습니까? (Hook)

**(독자의 문제점 자극 및 공감 유도)**

혹시 이런 고민 해보신 적 없으신가요?

> "지금 이 `User`의 잔액이 10만 원인 건 확실한데, **이 돈이 왜 10만 원이 되었는지** 그 과정(트랜잭션) 자체를 영구적으로 증명할 수 있는가?"

대부분의 개발자는 데이터베이스의 최종 '상태(State)'만 저장합니다. 사용자 잔액, 상품 목록, 주문 상태 등. 이 상태만 보면 당장은 문제가 없어 보입니다. 하지만 시스템이 커지고, 감사(Audit)의 요구사항이 복잡해지며, '어제 오후 3시에 이 사용자가 왜 이 결정을 내렸는지'에 대한 질문이 들어오는 순간, 기존의 CRUD 기반 DB는 한계에 부딪힙니다.

이런 상황에서 등장한 것이 **Event Sourcing**와 **CQRS**입니다. 둘 다 '좋은 아키텍처'의 대명사처럼 쓰이지만, 실제 현장에서는 이 둘을 어떻게 조합하고, 어느 부분에 '책임'을 둘지 끊임없이 논쟁이 벌어집니다.

이 가이드는 단순히 두 개념을 나열하는 것이 아닙니다. **'어떤 상황에서 무엇을 포기하고, 무엇에 책임을 지울 것인지'**에 대한 설계자 레벨의 논쟁 구조를 제시합니다.

## 📚 [본문 1] 핵심 개념 파헤치기: 왜 '상태'만으로는 부족한가?

### 1. 🧱 Event Sourcing (ES): 모든 것을 '기록'으로 간주하라
*   **개념:** 데이터의 상태를 직접 저장하는 대신, 그 상태에 도달하기까지의 모든 변경 이력(Event)을 순서대로 저장하는 방식입니다.
*   **비유:** 은행 계좌의 잔액(상태)을 저장하는 것이 아니라, `[입금 10만원]`, `[출금 3만원]`, `[이자 적립 1만원]` 이라는 **'거래 장부(Ledger)'** 자체를 원장(Event Store)에 기록하는 것과 같습니다.
*   **장점:** 시간 여행(Time Travel)이 가능하며, 시스템 감사(Audit)에 완벽합니다. 어떤 상태가 잘못되었는지 역추적하기 가장 쉽습니다.
*   **핵심 책임:** 모든 비즈니스 로직은 **이벤트 발생**을 중심으로 설계되어야 합니다.

### 2. ✂️ CQRS (Command Query Responsibility Segregation): 읽기와 쓰기를 분리하라
*   **개념:** 시스템의 '쓰기(Command)'와 '읽기(Query)'의 책임을 완전히 분리하는 아키텍처 패턴입니다.
*   **예시:** 사용자가 상품을 주문하는 행위(Command)는 복잡한 비즈니스 로직을 거쳐 DB에 기록됩니다. 하지만 사용자가 상품 목록을 보는 행위(Query)는 빠르고 단순해야 합니다. CQRS는 이 두 가지 경로를 최적화하기 위해 분리합니다.
*   **장점:** 각 영역에 맞는 최적화된 DB와 모델을 사용할 수 있어 성능 극대화가 가능합니다.
*   **핵심 책임:** **어떤 데이터는 쓰기 모델에, 어떤 데이터는 읽기 모델에 최적화**되어야 하는지 판단하는 설계 능력.

# 🚀 [Tech Wiki] GraphQL vs REST: 데이터 요청 최적화, 어떤 아키텍처를 선택해야 할까요?

데이터를 받아와서 몇 개를 쓰레기통에 버리고, 또 다른 데이터를 가져오기 위해 API를 여러 번 호출하는 **'다이얼로그 릴레이'** 같은 비효율적인 과정을 반복하면서, "도대체 왜 이 API는 이렇게 무거운 거야?"라는 한숨만 내쉬었을 때 말이죠.

만약 이 비효율이 단순히 개발자의 체력 문제가 아니라, 근본적인 **'아키텍처 선택'**의 문제라면 어떨까요?

## 💡 Introduction (도입부: 문제의 배경 설명)

요즘 웹 서비스의 복잡도는 매년 기하급수적으로 늘어나고 있습니다. 사용자 경험(UX)은 점점 더 빠르고, 더 개인화되어야 하죠. 이 모든 것을 뒷받침하는 것이 바로 **API (Application Programming Interface)**입니다.

API는 프론트엔드와 백엔드를 연결하는 '신경망'과 같아서, 서비스의 속도와 직결됩니다. 그리고 이 API를 설계하는 방식에 따라, 개발팀은 매번 거대한 **'기술적 의사결정 장애(Decision Paralysis)'**에 빠지게 됩니다.

가장 첨예하게 대립하는 두 아키텍처가 바로 **REST**와 **GraphQL**입니다.

REST는 수십 년간 표준처럼 사용되어 온, 믿음직하고 직관적인 방식입니다. 반면 GraphQL은 '필요한 것만 가져오라'는 개발자들의 간절한 염원에서 탄생한, 비교적 신흥 강자입니다.

둘 다 완벽하지 않습니다. 그리고 어느 하나가 무조건 답은 아닙니다.

## 💔 Pain Point (문제 제기: 독자의 고통을 구체화)

우리가 이 두 아키텍처 사이에서 고민해야 하는 근본적인 이유는, **'데이터 전송의 비효율성'**과 **'운영 책임의 트레이드오프'**라는 두 마리 토끼를 잡기 위함입니다.

### 1. 🔄 REST의 딜레마: 과도한 데이터 (Over-fetching)와 부족한 데이터 (Under-fetching)

REST는 '리소스(Resource)'를 중심으로 API 엔드포인트를 설계합니다. 예를 들어, `/users/{id}`라는 엔드포인트는 '사용자'라는 하나의 리소스를 가져옵니다.

문제는 이 리소스가 너무 '성실'하다는 것입니다. 사용자 이름, 이메일, 가입일, **그리고 이 서비스에서는 당장 필요 없는 10가지 추가 필드**까지 전부 보내줍니다. 이것이 바로 **Over-fetching**입니다.

결국 클라이언트는 이 거대한 데이터 덩어리에서 필요한 몇 개의 필드만 쏙 뽑아 쓰는, 비효율적인 과정을 거치게 됩니다.

더 큰 문제는, 사용자 정보와 그 사용자의 최근 주문 목록을 가져오려면 `/users/{id}`를 호출한 뒤, 또 `/users/{id}/orders`를 호출해야 하는 **'N+1 문제'**에 직면한다는 것입니다.

### 2. ⚙️ GraphQL의 딜레마: 설계의 복잡성과 배우는 곡선

GraphQL은 이 문제를 "클라이언트가 필요한 필드만 요청하면 된다"는 원칙으로 해결했습니다. 마치 '주문서'를 작성하듯, 내가 원하는 데이터 구조를 백엔드에 명시할 수 있죠.

하지만 이 편리함 뒤에는 그림자가 있습니다.

GraphQL은 그 구조적 유연성 때문에, API를 설계하는 초기 단계에서 **'어떤 데이터 모델을 기본으로 잡아야 할지'**에 대한 논쟁이 끊이지 않습니다. 데이터 구조를 한 번 잘못 잡으면, 나중에 서비스가 커질수록 아키텍처 전체를 수정해야 하는 막대한 비용이 발생할 수 있습니다. (이것이 바로 '개발팀의 피로도'를 높이는 지점입니다.)
