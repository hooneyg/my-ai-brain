### 💡 상세 분석 및 근거

#### 1. Microservices vs. Serverless (The Operational Trade-off)

*   **비교 근거:** 아키텍처의 경계 설정과 운영 책임의 분산 정도에 대한 논쟁.
*   **핵심 내용:**
    *   **Microservices:** 서비스 단위로 독립적인 배포가 가능하지만, 서비스 간 통신(네트워크 호출) 및 상태 관리(State Management)를 위한 인프라 복잡도가 높습니다.
    *   **Serverless (FaaS/BaaS):** 인프라 관리(OS 패치, 서버 용량 예측) 부담을 클라우드 제공자에게 위임하여 개발자는 비즈니스 로직에만 집중할 수 있습니다.
    *   **분석 포인트:** 트래픽 패턴(예측 가능한지, 급증하는지)과 팀의 운영 역량(DevOps 성숙도)에 따라 최적의 아키텍처가 달라지므로, 단순 비교가 아닌 '적용 시나리오' 비교가 중요합니다.
*   **예상 자료 출처:** AWS/Azure/GCP 아키텍처 가이드, ThoughtWorks 블로그, 주요 컨퍼런스(QCon, KubeCon) 발표 자료.

#### 2. GraphQL vs. REST (The Data Fetching Efficiency)

*   **비교 근거:** 클라이언트가 필요한 데이터 필드만 정확히 요청할 수 있는 데이터 페칭 방식의 우월성 여부.
*   **핵심 내용:**
    *   **REST:** HTTP 메서드(GET, POST 등)를 기반으로 자원(Resource) 중심으로 데이터를 설계합니다. 구조가 단순하고 범용적이지만, 종종 필요한 데이터가 아닌 필드까지 받아오는 **오버페칭(Over-fetching)** 문제가 발생합니다.
    *   **GraphQL:** 클라이언트가 원하는 데이터 구조(Schema)를 명시적으로 쿼리(Query)할 수 있게 합니다. 오버페칭 없이 필요한 데이터만 정확히 받아와 네트워크 부하를 최소화합니다.
    *   **분석 포인트:** GraphQL이 만능은 아니며, 캐싱 전략(Caching Strategy)이나 복잡한 비즈니스 로직 처리에 있어 REST의 강점이 여전히 존재합니다. 이 두 가지를 '상호 보완적' 관점에서 비교하는 것이 좋습니다.
*   **예상 자료 출처:** GraphQL 공식 문서, API 디자인 관련 아티클 (Stripe, Netflix 등 대규모 서비스 구현 사례), 클라이언트 라이브러리 비교 자료.

#### 3. Event-Driven Architecture (EDA) vs. Request-Response (The Decoupling Mechanism)

*   **비교 근거:** 시스템 컴포넌트 간의 의존성(Coupling) 관리 및 비동기 처리의 안정성.
*   **핵심 내용:**
    *   **Request-Response:** A가 B를 호출하고 즉각적인 응답을 받는 동기적 모델입니다. 간단하지만, A가 B의 가용성 및 응답 속도에 직접적으로 의존하게 됩니다.
    *   **EDA:** 컴포넌트가 직접 호출하는 대신, 특정 '이벤트(Event)'를 발행(Publish)합니다. 이 이벤트를 구독(Subscribe)하는 모든 컴포넌트가 비동기적으로 반응합니다. (메시지 큐, 스트림 플랫폼 활용)
    *   **분석 포인트:** EDA는 시스템의 결합도를 극단적으로 낮춰(Decoupling) 한 컴포넌트의 장애가 전체 시스템에 영향을 미치는 것을 막아줍니다. 그러나 이벤트 흐름을 추적하고(Tracing) 상태를 관리하는 것이 매우 복잡해지는 단점도 명확합니다.
*   **예상 자료 출처:** Apache Kafka/RabbitMQ 기술 백서, Event Sourcing 패턴 관련 논문, 분산 트랜잭션(Saga Pattern) 구현 사례.

### H2. 🧱 1. Microservices: 독립성과 경계의 명확성 (The Boundary Focus)
*   **H3. 개념 정의:** 애플리케이션을 독립적으로 배포 가능한 작은 서비스들의 집합. (예: 사용자 인증 서비스, 결제 서비스 등)
*   **H3. 장점 (The Power):**
    *   **기술 독립성 (Polyglot Stacks):** 각 서비스별로 최적의 언어/DB 사용 가능.
    *   **격리성 (Fault Isolation):** 한 서비스의 장애가 전체 시스템을 마비시키지 않음.
    *   **확장성 (Scalability):** 트래픽이 몰리는 특정 서비스만 선택적으로 확장 가능.
*   **H3. 단점 (The Overhead):**
    *   **운영 복잡성 (Operational Overhead):** 서비스 간 통신(Inter-service Communication)을 위한 서비스 메시(Service Mesh), API 게이트웨이 등 인프라 구성이 복잡함.
    *   **트랜잭션 관리:** 분산 트랜잭션(Saga 패턴 등) 구현 난이도가 매우 높음.
    *   **비용:** 운영하는 인프라 자원(VM, 컨테이너)에 대한 지속적인 비용 지출이 발생함.

#### 🔑 핵심 메시지 (Key Takeaways)
1.  Microservices는 **'개발팀의 운영 역량(DevOps Maturity)'**에 가장 크게 의존한다.
2.  '독립적인 배포'라는 장점을 얻기 위해 '운영의 복잡성'이라는 대가를 치러야 한다.
3.  상태(State)와 트랜잭션 관리는 여전히 개발자가 가장 깊이 고민해야 할 부분이다.

## 📚 Git 오류 분석 리포트: `fatal: couldn't find remote ref main`

이 오류는 Git이 원격 저장소(Remote Repository, 예: GitHub)에서 특정 브랜치(여기서는 `main`)를 찾으려고 시도했으나, 해당 이름의 브랜치를 찾을 수 없을 때 발생하는 대표적인 네트워크/브랜치 참조 오류입니다.

이 오류는 단순히 '네트워크 연결 문제'가 아니라, **Git이 인식하는 원격 저장소의 구조적 문제**를 의미합니다.

---

### 💡 오류의 기술적 배경 지식

| 항목 | 설명 | 엔지니어링 관점의 이해 |
| :--- | :--- | :--- |
| **`fatal`** | 치명적 오류(Fatal Error)를 의미하며, Git 명령 실행을 즉시 중단시킵니다. | 시스템이 필수 전제 조건(여기서는 `main` 브랜치 존재)을 충족하지 못했음을 뜻합니다. |
| **`remote ref`** | 원격 저장소(Remote)에 있는 참조(Reference)를 의미합니다. Git에서 '참조'는 브랜치 이름이나 태그 이름 같은 포인터를 말합니다. | Git이 원격 서버에서 브랜치 이름으로 사용되는 포인터를 찾지 못했다는 뜻입니다. |
| **`couldn't find`** | 찾을 수 없다(Not Found)는 의미입니다. | 가장 핵심적인 원인: 원격 저장소에 `main`이라는 이름의 브랜치가 존재하지 않거나, 이름이 다릅니다. |

---

### 🔍 발생 원인별 진단 및 해결책 (Troubleshooting Guide)

가장 가능성이 높은 3가지 원인과 그에 따른 해결책을 제시합니다.

#### 1. 🏷️ 원인: 브랜치 이름 변경 또는 불일치 (가장 흔함)
*   **상황:** 과거에는 기본 브랜치 이름이 `master`였으나, 최신 관행에 따라 `main`으로 변경되었습니다. 로컬 환경은 `main`을 참조하려고 하지만, 원격 저장소의 실제 기본 브랜치는 `master`일 수 있습니다.
*   **진단:** 원격 저장소의 실제 브랜치 목록을 확인합니다.
*   **해결책:**
    *   **① 원격 브랜치 목록 확인:**
        ```bash
        git branch -r
        ```
        (출력된 목록에 `master`가 있는지 확인합니다.)
    *   **② 로컬 브랜치 이름을 원격에 맞게 변경:**
        ```bash
        git branch -m main master  # 로컬 main을 master로 변경 (예시)
        ```
    *   **③ 원격 브랜치를 강제로 추적:**
        ```bash
        git fetch origin
        git checkout master # 실제 존재하는 이름으로 체크아웃
        ```

#### 2. 🔌 원인: 원격 저장소 연결 또는 동기화 실패
*   **상황:** 로컬 저장소가 원격 저장소의 최신 상태를 반영하지 못했거나, 원격 저장소 자체가 일시적으로 접근 불가능할 때 발생합니다.
*   **진단:** 네트워크 연결 및 원격 저장소 권한을 확인합니다.
*   **해결책:**
    *   **① 강제 동기화:**
        ```bash
        git fetch --all
        ```
    *   **② 원격 연결 확인:**
        ```bash
        git remote -v
        ```
        (출력된 URL이 올바른지 확인합니다.)

#### 3. 🗑️ 원인: 브랜치 미푸시 또는 삭제
*   **상황:** 로컬에서만 생성된 브랜치이거나, 원격 저장소에서 실수로 해당 브랜치가 삭제된 경우입니다.
*   **진단:** 원격 저장소에 해당 브랜치가 실제로 존재하는지 웹 UI(GitHub 등)에서 직접 확인합니다.
*   **해결책:**
    *   **① 브랜치 푸시 (로컬 -> 원격):**
        ```bash
        git push -u origin [브랜치명]
        ```
    *   **② 브랜치 재설정:** 만약 `main`이 삭제된 것이 확실하다면, 필요한 내용을 다시 커밋하고 푸시하는 과정이 필요합니다.

# 📚 Tech Wiki 초안: Git Sync 오류 해결 가이드 (feat. fatal: couldn't find remote ref main)

## 🚀 도입: "이거 또야?" 에러 메시지 앞에서 당황했다면?

안녕하세요, 후니즈닷컴 독자 여러분! 개발하다 보면 누구나 한 번쯤 마주치는 'Git 에러'가 있습니다. 그중에서도 `fatal: couldn't find remote ref main` 같은 메시지를 보면, 마치 시스템이 갑자기 문을 닫아버린 것 같은 당황스러움이 느껴지죠.

이 에러 메시지는 단순히 "뭔가 잘못되었다"라는 뜻을 넘어, **Git이 여러분의 로컬 컴퓨터와 원격 저장소(GitHub 등) 사이에서 길을 잃었다**는 신호입니다. 걱정 마세요! 이 가이드에서는 이 에러가 발생하는 근본적인 이유와, 마치 친구에게 물어보듯 친절하게 해결하는 방법을 단계별로 알려드릴게요.

---

## 🔍 1. 에러의 정체 파헤치기: 'remote ref'가 뭔가요? (비전공자 비유)

우선, 이 에러 메시지에 등장하는 핵심 용어부터 이해해야 합니다.

### 💡 핵심 용어 설명

*   **Git:** 버전 관리를 해주는 만능 비서입니다. 여러분의 코드 변화를 시간여행처럼 기록해 주는 역할을 하죠.
*   **Remote Repository (원격 저장소):** 회사 서버에 보관된, 모든 팀원이 공유하는 '공식 백업본'입니다. (GitHub 같은 곳이 대표적이죠.)
*   **Branch (브랜치):** 프로젝트의 '특정 버전'입니다. 메인 코드를 건드리지 않고, 새로운 기능을 실험해 볼 때 사용하는 별도의 작업 공간이라고 생각하면 쉬워요. (예: `feature/login` 브랜치)
*   **`remote ref`:** 원격 저장소에 존재하는 '브랜치 이름의 포인터(지시자)'입니다.

### 📘 에러의 비유적 해석

**`fatal: couldn't find remote ref main`** 이라는 에러는 마치 이렇게 해석할 수 있습니다.

> "팀장님(Git)이 원격 서버(GitHub)에 가서 '메인 버전(main)'을 찾아보려고 했는데, **실제 서버의 안내 책자(ref)에 'main'이라는 이름의 버전이 없습니다.**"

즉, 로컬 환경은 'main' 브랜치를 기준으로 작업하려 하지만, 원격 저장소의 실제 기본 브랜치 이름은 'master'이거나, 이름이 완전히 다를 때 발생하는 **이름 불일치(Mismatch)**가 가장 흔한 원인입니다.

---

## 🛠️ 2. 문제 진단 및 해결책: 상황별 대처법

에러를 만났을 때, 무작정 명령어를 돌리기보다 원인을 먼저 진단하는 것이 중요합니다.

### 🟢 Case 1: 가장 흔한 경우 - 브랜치 이름 불일치 (Master vs. Main)

**[진단]** 가장 유력한 원인입니다. 예전에는 기본 브랜치 이름을 `master`로 많이 사용했지만, 최근에는 `main`으로 통일하는 추세입니다.

**[해결책]** 원격 저장소에 *실제로 존재하는* 브랜치 이름을 확인하고, 로컬 브랜치 이름을 그에 맞춰 수정해 줘야 합니다.

1.  **원격 브랜치 목록 확인하기 (🕵️‍♂️ 탐정 모드):**
    ```bash
    git branch -r
    ```
    *(출력 결과를 잘 살펴보세요. `origin/master` 같은 이름이 보이는지 확인합니다.)*
2.  **로컬 브랜치 이름 수정하기 (✨ 이름 바꾸기):**
    만약 원격에 `master`가 있고, 로컬에 `main`이 있다면, 로컬의 `main`을 `master`로 바꿔줍니다.
    ```bash
    git branch -m main master
    ```
3.  **다시 원격과 동기화하기 (🔄 싱크 완료):**
    ```bash
    git pull origin master
    ```

**[해결책]** 가장 기본적인 점검을 수행합니다.

1.  **인터넷 연결 확인:** 당연하지만, 가장 먼저 체크합니다.
2.  **자격 증명(Credential) 재확인:** GitHub 등 원격 저장소의 접근 토큰(Access Token)이 만료되었거나 잘못되었을 수 있습니다. 해당 서비스의 자격 증명을 재설정해야 합니다.

## 🚀 Git Sync 오류 해결을 위한 4단계 명령어 시퀀스

이 시퀀스는 로컬 저장소가 원격 저장소의 최신 브랜치 구조를 알지 못하거나, 기본 브랜치 이름이 `main`이 아닌 `master`일 때 발생하는 문제를 포괄적으로 해결합니다.

### 🔍 0단계: 현재 상태 진단 (Diagnostic Check)
가장 먼저 로컬 저장소의 상태와 원격 저장소의 모든 정보를 가져와서 오류의 근본 원인을 파악합니다.

```bash
# 1. 현재 로컬 브랜치 상태 확인
git status
# 목적: 현재 어떤 브랜치에 있는지, 커밋이 남아있는지 확인합니다.

# 2. 모든 원격 브랜치 정보 강제 다운로드
git fetch --all
# 목적: 로컬에 캐시된 원격 브랜치 정보(Remote Ref)를 강제로 최신 상태로 업데이트합니다.
# 이 과정이 오류의 핵심인 '정보 부족'을 해결하는 첫걸음입니다.
```

### 💡 1단계: 원격 브랜치 목록 확인 (Diagnosis)
`fetch`를 통해 정보를 업데이트했으므로, 이제 원격 저장소에 **실제로 존재하는 브랜치 이름**을 확인해야 합니다.

```bash
# 원격 저장소에 존재하는 모든 브랜치 목록 확인
git branch -r
# 출력 예시:
# * origin/HEAD -> origin/master
#   origin/develop
#   origin/master  <-- 이 부분이 실제 브랜치 이름일 확률이 높습니다.
```
**[핵심 로직]** 만약 `git branch -r`의 결과에 `origin/main`이 없고 `origin/master`만 있다면, 로컬의 기본 브랜치 이름이 틀린 것입니다.

### 🛠️ 2단계: 로컬 브랜치 이름 수정 (Remediation - Case 1: master로 변경된 경우)
만약 1단계에서 원격 브랜치가 `master`임을 확인했다면, 로컬의 기본 브랜치 이름을 원격에 맞게 수정해야 합니다.

```bash
# 1. 로컬의 'main' 브랜치를 'master' 브랜치로 이름 변경
git branch -m main master
# 목적: 로컬 브랜치 이름 자체를 원격 구조에 맞게 수정합니다.

# 2. 변경된 브랜치 이름을 원격 저장소에 푸시 (강제 푸시 필요)
git push origin master --force
# 목적: 로컬의 이름 변경을 원격에도 반영합니다.
```

### 🔄 3단계: 최신 코드로 동기화 (Final Sync)
이제 이름 충돌 문제가 해결되었으므로, 최신 코드를 안전하게 가져와 작업합니다.

```bash
# 1. 수정된 'master' 브랜치로 이동
git checkout master
# 목적: 작업할 브랜치로 HEAD 포인터를 옮깁니다.

# 2. 원격의 최신 내용을 로컬로 병합 (Pull)
git pull origin master
# 목적: 원격 저장소의 모든 커밋을 가져와 로컬 브랜치를 최신 상태로 만듭니다.
```

### 📝 요약: 문제 해결의 논리 흐름 (Flow Summary)

1.  **`git fetch --all`**: "야, 서버에 무슨 브랜치들 있어? 전부 다 알려줘." (정보 업데이트)
2.  **`git branch -r`**: "알려준 거 중에 진짜 브랜치 이름은 뭐야?" (진단)

4.  **`git checkout master` + `git pull origin master`**: "이제 네가 알려준 그 이름으로 코드를 받아와서 작업할게." (실행 및 동기화)

걱정 마세요. 이 에러는 단순한 네트워크 문제가 아니라, **여러분의 로컬 환경과 원격 저장소(GitHub 등)가 서로 다른 '언어'를 사용하고 있기 때문에 발생하는 구조적 충돌**입니다. 이 가이드에서는 문제의 정의부터 완벽한 해결책까지, 단계별로 설명해 드립니다.

---

## 🔍 1. 문제 정의: 이 에러가 의미하는 것

### 💡 핵심 개념: `remote ref`란?
Git에서 '참조(Reference, ref)'는 브랜치 이름이나 태그 이름 같은 일종의 **포인터(지시자)**를 의미합니다. `remote ref`는 원격 저장소에 **실제로 존재하는 브랜치 이름의 포인터**를 뜻합니다.

### 🚨 에러 해석
`fatal: couldn't find remote ref main` 이라는 메시지는 다음을 의미합니다.
> "Git이 원격 서버(GitHub)에 가서 `main`이라는 이름의 브랜치를 찾아보려고 했는데, **실제 서버의 안내 책자(Ref)에 'main'이라는 이름의 버전이 없습니다.**"

로컬 환경은 최신 트렌드에 맞춰 `main` 브랜치를 기본으로 사용하려 하지만, 원격 저장소는 여전히 과거의 기본 이름인 `master`를 사용하고 있을 때 가장 흔하게 발생합니다.

---

## ⚙️ 2. 근본 원인 분석: 왜 이런 충돌이 생길까요?

가장 높은 확률로 발생하는 원인은 **브랜치 이름의 불일치(Mismatch)**입니다.

### 🎯 원인 1: Master vs. Main (가장 흔함)
*   **배경:** 과거에는 대부분의 Git 저장소가 기본 브랜치 이름으로 `master`를 사용했습니다. 하지만 최근 업계 표준과 커뮤니티의 트렌드가 `main`으로 변경되면서, 로컬 환경은 `main`을 따르고 원격 저장소는 여전히 `master`를 고수하는 상황이 발생합니다.
*   **결과:** 로컬은 `main`을 기준으로 작업을 시작하려 하지만, 원격은 `main`이라는 브랜치 자체가 없다고 판단하여 오류를 냅니다.

### 🎯 원인 2: 동기화 실패 (Stale Cache)
*   원격 저장소의 브랜치 구조가 변경되었음에도 불구하고, 로컬 저장소의 캐시(Cache)가 업데이트되지 않아 오류가 발생할 수 있습니다.

---

## 🛠️ 3. 해결 방법: 4단계 명령어 시퀀스 (Step-by-step)

이 해결책은 **'진단 → 수정 → 동기화'**의 3단계 프로세스로 진행됩니다. 터미널에서 순서대로 실행해 주세요.

### 🟢 Step 1: 원격 정보 강제 업데이트 (Diagnosis)
가장 먼저, 로컬 저장소에 캐시된 정보를 모두 버리고 원격 저장소의 최신 구조를 가져옵니다.

```bash
# 1. 모든 원격 브랜치 정보 강제 다운로드
git fetch --all
```

### 🟡 Step 2: 실제 브랜치 이름 확인 (Diagnosis)
원격 저장소에 **실제로 존재하는** 브랜치 목록을 확인하여, 기본 브랜치 이름이 `main`인지 `master`인지 파악합니다.

```bash
# 2. 원격 브랜치 목록 확인 (★ 이 결과가 핵심입니다)
git branch -r
```
*   **🔍 확인 결과가 `origin/master`만 있다면:** 기본 브랜치는 `master`입니다.
*   **🔍 확인 결과가 `origin/main`이라면:** 다른 문제가 있을 수 있으니 다음 단계로 넘어갑니다.

### 🔴 Step 3: 로컬 브랜치 이름 수정 및 푸시 (Remediation)
Step 2에서 원격 브랜치가 `master`임을 확인했다면, 로컬 브랜치 이름을 원격에 맞게 수정해야 합니다.

```bash
# 1. 로컬의 'main' 브랜치를 'master' 브랜치로 이름 변경
git branch -m main master

# 2. 이름이 변경된 브랜치를 원격 저장소에 강제로 반영 (주의: 반드시 필요한 경우에만 사용)
git push origin master --force
```

### 🔵 Step 4: 최신 코드로 동기화 (Final Sync)
이제 이름 충돌 문제가 해결되었으므로, 안전하게 최신 코드를 가져와 작업을 시작합니다.

```bash
# 1. 수정된 'master' 브랜치로 이동
git checkout master

# 2. 원격의 최신 코드를 가져와 로컬과 동기화
git pull origin master
```

### 🧪 시나리오 1: 로컬 브랜치 강제 리셋 및 동기화 (Master $\rightarrow$ Feature)

**상황:** 로컬 `master` 브랜치에 커밋하지 않은 중요한 변경사항이 남아 있어, 원격 저장소의 최신 상태로 강제 동기화해야 할 때.

#### ❌ 실패 케이스 (Failure Case): 원격 변경 사항 무시 시도
로컬 변경사항을 커밋하지 않은 상태에서 강제 푸시를 시도하면, Git은 데이터 손실 위험 때문에 경고를 발생시키거나 실패합니다.

```bash
# 1. 로컬에서 작업 파일 변경 (커밋 안 함)
echo "temp_data_fail" > local_file.txt

# 2. 원격 브랜치에 강제 동기화 시도 (실패 예상)
git pull origin master --force
# 🚨 예상 오류 메시지:
# error: Your local changes to local_file.txt have been overwritten by merge.
#       Please commit or stash them before merging.
```

#### ✅ 성공 케이스 (Success Case): 변경사항 임시 보관 후 강제 리셋
로컬 변경사항을 `stash`로 임시 보관한 후, 원격 브랜치 상태로 리셋하고, 이후에 변경사항을 다시 적용합니다.

```bash
# 1. 로컬 변경사항 임시 보관 (Stash)
git stash push -m "pre-force-pull stash"

# 2. 원격 브랜치 상태로 강제 리셋 및 동기화 (Success)
git fetch origin
git reset --hard origin/master 

# 3. 로컬 변경사항 복구 (선택 사항)
git stash pop 

# 4. 최종 검증
git status
# ✅ 기대 결과: nothing to commit, working tree clean
```

### 🧪 시나리오 2: 브랜치 이름 변경 (Rename)

**상황:** 개발 중이던 `feature/old-api` 브랜치 이름을 더 명확한 `feature/new-api`로 변경해야 할 때.

#### ❌ 실패 케이스 (Failure Case): 브랜치 이름 변경 전 커밋 미반영
로컬에서 작업한 내용이 커밋되지 않은 상태에서 브랜치 이름을 변경하면, Git이 작업의 일관성을 위해 경고하거나 실패할 수 있습니다.

```bash
# 1. 로컬에서 작업 파일 변경 (커밋 안 함)
echo "temp_data_fail" > local_file.txt

# 2. 브랜치 이름 변경 시도 (실패 예상)
git branch -m old-api-to-new-api
# 🚨 예상 오류 메시지:
# error: Your local changes to local_file.txt have been overwritten by rename.
#       Please commit or stash them before renaming.
```

#### ✅ 성공 케이스 (Success Case): 변경사항 커밋 후 이름 변경
작업 내용을 커밋한 후 브랜치 이름을 변경하는 것이 가장 안정적입니다.

```bash
# 1. 로컬 변경사항 커밋
git add .
git commit -m "feat: Finalizing before rename"

# 2. 브랜치 이름 변경 (Success)
git branch -m feature/old-api feature/new-api

# 3. 원격 브랜치 이름 변경 (필수)
git push origin feature/new-api --force
# (만약 old-api가 원격에 존재한다면, 삭제 및 새 이름으로 푸시하는 과정이 필요합니다.)

# 4. 최종 검증
git branch
# ✅ 기대 결과: * feature/new-api
```
